# Статическая поставка frontend

Сборка полностью выполняется на Mac в локальном Docker. При обновлении production копируется только содержимое `dist/`; Node, Vite, npm, исходники, node_modules, тесты, .env и Docker-файлы серверу не нужны.

## Локальная сборка

В общем workspace BMS_Monitor:

```sh
./bin/sync-contract --check
docker compose exec -T frontend sh -c 'npm run check:generated && npm run lint:contract && npm run lint && npm run typecheck && npm test && npm run build'
```

Для отдельно полученного frontend-репозитория, из его корня, с Docker и меткой текущей локальной сессии:

```sh
docker run --rm --label "ao.session=${AO_SESSION_ID:?}" --memory 512m --cpus 1 \
  -v "$PWD:/app" -w /app node:22-alpine \
  sh -c 'npm ci && npm run check:generated && npm run lint:contract && npm run lint && npm test && npm run build'
```

`build` включает проверку TypeScript. Не менять lock-файл на сервере и не использовать Vite dev/preview как production-сервер. Известное ограничение инструментов: на предыдущей проверке picomatch 4.0.7 имел GHSA-fc5q-39xc-vjpf; наличие готового исправления проверяется отдельно перед поставкой. Это относится к цепочке локальной сборки, а не к серверному Node-процессу: такого процесса нет.

## Правило повторного обновления

После явного поручения владельца обновить production проверить доступ по SSH `lex@192.168.1.5` и фактический каталог `/home/lex/www/bms_monitor/frontend/public`. Если путь неизвестен или не совпадает, остановиться до уточнения. Backend обновляется отдельно через Git.

Загрузить готовые файлы из локального `dist/`: сначала хешированные ресурсы, затем заменить `index.html`. Сохранить прежние ресурсы для уже открытых страниц и отката; не удалять существующие серверные файлы и не выгружать исходники, зависимости или документы вместе с обновлением. После передачи сверить файлы сборки и проверить загрузку страницы/API. Само описание не разрешает доступ или деплой без поручения владельца.

## Размещение

Целевой каталог `/home/lex/www/bms_monitor/frontend`:

```text
frontend/
  public/
    index.html
    assets/...
  docs/deployment.md
  README.md
  SHA256SUMS
```

`public/` содержит готовые сборки `dist/`; прежние хешированные ресурсы могут сохраняться после обновления. Nginx root должен указывать на `frontend/public`, не на весь каталог проекта. `SHA256SUMS` фиксирует файлы поставки и позволяет сверить передачу командой `sha256sum -c SHA256SUMS` из frontend. Документация и манифест не предназначены для веб-раздачи. Существующие файлы соседних проектов не затрагиваются.

Сборка рассчитана на корень выбранного origin, например `http://192.168.1.5:SITE_PORT/`. Порт определяет DevOps. API и Mercure доступны на этом же origin; в JS нет адреса Docker backend или JWT. Сборка не требует production-паролей и не зависит от выбранного порта сайта.

## Маршруты для DevOps

| Путь | Обработка |
| --- | --- |
| `/` | `public/index.html` |
| `/assets/*` | Существующий файл из public/assets; отсутствующий — 404 |
| `/api/*` | Backend PHP-FPM; не заменять ответы на index.html |
| `GET /.well-known/mercure` | Нативный Mercure hub; query сохраняется, буферизация/кеш отключены |

Страницы интерфейса (`#overview`, `#history`, `#history/cells`, `#history/cells/N`, `#history/energy`, `#history/events`, `#configuration`) — часть адреса после `#`, браузер не отправляет её серверу; отдельные серверные маршруты для них не нужны.

Для index.html — перепроверка кеша при открытии (`Cache-Control: no-cache`). Для файлов с хешем в assets допустим длительный immutable-кеш. Значок сайта и манифест (`assets/favicon.svg`, `assets/apple-touch-icon.png`, `assets/icon-192.png`, `assets/icon-512.png`, `assets/manifest.webmanifest`) лежат там же без хеша в имени: их отдаёт существующий маршрут `/assets/*`, но immutable-кеш к ним применять нельзя. SSE — длительное соединение с heartbeat, а не обычный короткий HTTP-ответ; POST к публичному пути Mercure не разрешать. Подробности переменных, сервера и издателя — `backend/docs/deployment.md` в отдельном backend checkout.

## Порядок обновления и Nginx

Сначала обновляется и проверяется backend (новые `GET /api/v1/battery/history/series?…&set=overview|cells`, `/api/v1/battery/energy/daily`, `/api/v1/battery/events`), затем выгружается frontend. Если выгрузить frontend раньше, прежний backend отклонит новые запросы (`series` с `set` — 422, `energy/daily` и `events` — 404), и интерфейс покажет следующее: графики страницы истории — «Історія недоступна»; строки «За 24 год» на главном экране — «За 24 год: немає даних»; колокольчик не подсвечивается; вкладка «Енергія» — «Не вдалося оновити дані про енергію…»; журнал «Події» — «Не вдалося завантажити журнал…». Текущие показания и расчётное время работают, потому что используют прежние запросы. Поэтому обратный порядок недопустим. Прежний frontend с новым backend работает: ответ `series` без `set` не изменился.

Замечания для Nginx (настраивает DevOps по отдельному поручению):
- включить сжатие JSON (`gzip_types application/json`) для `/api/*`: ответы `series` с `set` за год и `energy/daily?range=1y` заметно больше прежних;
- значок и манифест (`assets/favicon.svg`, `assets/apple-touch-icon.png`, `assets/icon-*.png`) — обычный короткий кеш или перепроверка, не immutable;
- `assets/manifest.webmanifest` отдавать с типом `application/manifest+json`.

## Поведение и проверка

Frontend подписывается на `urn:bms:battery:sacred-sun-monitor-01`, получает `/api/v1/telemetry/state`, отдельно — `/api/v1/battery/history/series?range=10m|1h|12h|24h|30d|3mo|1y[&set=overview|cells]`, `/api/v1/battery/energy/daily?range=30d|3mo|1y` и `/api/v1/battery/events?limit=…[&before=…]`. По одному SSE принимает `telemetry.updated.v1` и `history.updated.v1`; версия подготовки истории независима от версии измерения. Каждый потребитель объединяет сигналы сам: главный экран — `series?range=10m` не чаще 15 секунд, две сводки за 24 часа и колокольчик — не чаще 60 секунд и только при росте версии подготовленной истории; страница истории — один запрос открытой вкладки. Обычно это 4–5 запросов в минуту с открытого главного экрана, а пока backend готовит новые сводки — до ~7 в минуту. Запрос выполняется только после сигнала; периодического опроса нет. Выбор периода немедленно обновляет историю без нового SSE или снимка текущего состояния. При возвращении к вкладке и восстановлении соединения повторно получает выбранный снимок. Подготовка сводных интервалов показана отдельно от пропусков; при незавершённой подготовке общий процент полноты неизвестен. При ошибке сохраняется предыдущий подписанный снимок.

Пауза источника — нормальное «Немає нових вимірювань» с пробелами истории; неизвестные показатели не заменяются нулями. Работоспособность hub не доказывает наличие данных батареи. Нет пользователей/паролей приложения: доступ ограничивается внутренней сетью на сервере.

После настройки DevOps проверяет загрузку index/assets, правильные JSON-ответы API, SSE и обновление по реальному пакету. До настройки backend/hub загруженный интерфейс может показывать ошибку связи — простое копирование файлов не запускает систему. Эмулятор, годовые отчёты и доработка монитора в эту поставку не входят. Дашборд и правила отображения истории описаны в README.md.
